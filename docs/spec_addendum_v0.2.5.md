# Specification Addendum v0.2.5

This addendum **amends no rule** of `docs/formal_specification_v0.2.md`. It records the readings that the analysis-run record, the source binding, the absolute-URI mapping and the coverage gates (Milestone 5) rely on, so that they are reviewable as readings. Addenda `v0.2.1`–`v0.2.4` are unchanged; G18/P-3 is not reopened and no contradiction with it was found (relative to the same artifact without a record, a record can only add a binding, remove refusals by deciding them, or - the one case that raises a verdict - supply a declared full-coverage claim that §5.1 step 2 itself says is what `Absent` requires, capped at Weak by the provenance ladder, §5). There are still exactly three verdicts and six evidence states.

## 1. Reading: a run record is an assertion, a hash match is not a proof of anything but identity of bytes

* A record (`analysis-run/1`) is a statement by its author. Written by the recorder (`python -m analysis_runner`) it reports observations the recorder made; read back from a file it is still only JSON, so `origin` and `field_sources` are statements.
* A SHA-256 in the record equal to the SHA-256 of the artifact shows that the record describes **those bytes**. It does not show that an analyzer produced them, that the result is trustworthy or that it covers anything. A mismatch (or an artifact the record does not list) means the record does not describe this artifact: nothing in it is applied (binding CONTRADICTED / MISSING).
* §1.2: P2 requires the *document* to declare a digest equal to S's artifact digest; P3 additionally requires a verified signature for the content in question. A log or an unauthenticated record can do neither, so a document derived from them is **never P2 or P3** (P1 at most, and only when the tool, version and time are known). A detached verification result cannot lift it either, because P3 needs P2 first. The record carries no state, level, BIND result, trust statement or verdict and cannot say that a field was verified.

## 2. Reading: what identifies "the source that was analysed" (§5.1 BIND)

BIND binds the analysis to the artifact and component version. The analysed source is identified by repository, **full** revision and a digest of the analysed tree; a repository URL, branch, name, file name or version string is not an identity. The binding of a record to the evaluator's `AnalysisSubject` has exactly five outcomes:

| Status | Meaning (examples) |
|---|---|
| `established` | repository equal; full revisions equal; tree digest equal when the evaluator declared one; clean tree, no untracked or ignored files, no unpinned submodule, not changed during the run, **observed** (not merely absent); output hash, tool, target, root consistent |
| `missing` | a required identity fact is not stated by one side (unobserved cleanliness is *not* "clean") |
| `contradicted` | two statements of one fact differ (revision, repository, digest, target, tool, root, output hash) |
| `ambiguous` | an abbreviated revision; submodules whose checked-out content is not identified |
| `impossible` | the commit cannot identify the analysed bytes: modified or untracked tree, change during the run |

A dirty tree can still be identified exactly by a digest of its **contents** that the evaluator declared as the assessed source's identity (`sha256-worktree:`), because then the identity rests on content, not on the commit. Only `established` lets a derived document carry the assessed artifact; every other status keeps the observation (an unbound positive can only lower a verdict, P-3) and leaves BIND Unknown (R6). The link between the analysed source and the assessed artifact S stays an evaluator statement (`SOURCE_TO_ARTIFACT_LINK_EVALUATOR_ASSERTED`); no record establishes it.

## 3. Reading: mapping an absolute location to the analysed source

A location that is an absolute URI is mapped into the analysis root **only** if (a) a record declares the root (a normalized absolute POSIX path, role `primary`, `vendored` or `external`; roots may not overlap), (b) the binding of that record to the assessed source is `established`, (c) the URI is a `file` URI without a remote host, (d) its decoded path lies under the root by whole path segments, with no `.`/`..`/empty segment, no encoded separator or NUL and no query or fragment. Anything else stays unresolved. The path comparison is case-sensitive; symbolic links and case-folding file systems are not resolved or assumed (a record's roots are taken as canonical, which is why dot segments are rejected instead of normalized). A location under a non-primary root is never a location of the assessed tree: if its path inside that root ends with a locus file it is **undecidable**, otherwise irrelevant. Unmapped locations keep the previous milestone's procedure (relevant → undecidable → refusal beside a K1 absence), whose necessary-condition test is widened here to "the path ends with the target-root-qualified locus file **or the bare locus file**" (only more locations are kept).

## 4. Reading: coverage is a set of separate facts

§5.1 step 2 makes `Absent` depend on a K1 report that **declares** a full-coverage claim over LOCUS and ENTRY (A6: soundness is recorded as claimed). Process success, an empty `results`, an empty `codeFlows`, schema validity and a locally generated manifest are none of that. The implementation therefore evaluates these facts separately (none implies another): binding established; tool declared (name and version); stages completed with exit 0 and the artifact not reporting failure; extraction stage completed; language scope recorded; locus included in the analysed scope (SARIF `expected-extracted-files` notifications, else the record's own file inventory, GraphML locus METHOD found); query suite completed with its identity corroborated by the artifact when it lists packs and rules; **claim semantics** (the query is a locus-reachability analysis for SARIF, the export is a call graph for GraphML; a stock taint query is declared as such and does not qualify); entry points enumerated (a declared inventory, consistent with the evaluator's entry set and, for graphs, present in the export); exclusions and suppressions accounted for; no partial-analysis indicator or error; no undecidable evidence; and the record's coverage claim declared and covering the evaluated locus.

*What the tools can establish.* CodeQL SARIF states its extracted-files scope, query packs and rules, and the success of the run; it states nothing about entry points or about whether a query reasons about reachability of an arbitrary locus. A Joern GraphML export states neither tool, scope, entry points nor which passes ran, and a per-method (`--repr cpg`) export drops cross-method calls. **No supported representation enumerates entry points**, so entry-point completeness is, at best, a declaration by the record's author (A3 permits the evaluator or the analysis to supply it); it is never inferred from default configuration, from a successful run or from CALL edges.

## 5. Reading: when a negative K1 report may be derived

Only when **all** facts of §4 are established, nothing is recorded as a path and nothing is undecidable, is a K1 report with `finding = negative` and a *declared* full-coverage claim derived from the artifact, carrying the record's declared entry-point completeness and analysed configurations. Whether that yields `Absent` is then decided by the existing rules, unchanged: its provenance is at most P1 (§1), so R13 holds the verdict at **Weak**, and hazards and configuration are decided as for any K1 report. A record-derived absence therefore cannot be Supported. Anything missing leaves REACH Unknown (R2) and the verdict Insufficient; the list of conditions that prevented a stronger conclusion is reported with the result. Next to a recorded path the path decides (R1); next to a supplied K1 absence the path conflicts (R3); a derived absence next to an unresolved relevant record of another artifact is refused like any absence (addendum v0.2.4 §1).

One engine change was needed and is not a rule change: a derived document with a negative finding has no observation trace, so the item builder now gives it the ordinary report-level REACH item (`#/finding`) instead of silently producing none (`evidence/reach_items.py`, `evidence/reach_evaluator.py`). The item is validated exactly like a strict-input K1 report.

## 6. What stays open

Authentic Joern output; an entry-point inventory produced by an analyzer; a revision source inside CodeQL's own SARIF; verification of a record's claims (cryptographic verification is not implemented); the S-link (G17); the aggregation of overlapping reports (G8/U-9); the list-level provenance mapping (G7).
